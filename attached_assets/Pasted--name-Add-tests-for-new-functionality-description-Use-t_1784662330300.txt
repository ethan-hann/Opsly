name: Add tests for new functionality
description: Use this skill when adding, changing, or fixing behavior in the codebase — new functions, endpoints, components, bug fixes, or refactors. Ensures every change ships with passing tests in the same task, so testing doesn't get proposed as separate follow-up work.
---
**Activation:** On-demand — fires when a code change alters observable behavior. Guardrail: it shapes what Agent builds (tests alongside the change) and runs the suite before the task is called done.

# Instructions

A change is complete only when it ships with tests that verify it. AI agents often propose "add tests" as a follow-up task — treat that as the failure mode this skill exists to prevent. If you're about to suggest testing as a next step, write the tests now instead.

- Applies to: new functions, endpoints, and components; bug fixes (add a test that fails on the old code and passes on the fix); and refactors that change observable behavior. Skip only changes with nothing to verify — formatting, comments, copy tweaks, no-op dependency bumps — and say so in one line when you do.
- Match the existing setup: check `package.json`, `pyproject.toml`, `go.mod`, and similar for the test runner already in use, and mirror the location and naming of existing test files. Don't add a second framework alongside one that's already there. If none exists, add the ecosystem default (Vitest or Jest for JS/TS, pytest for Python, the built-in `testing` package for Go) plus a one-command `test` script so the suite is runnable.
- Cover three cases per unit of behavior: the happy path; edge cases (empty/null/zero, boundaries, large or unicode input); and error handling (invalid input, thrown exceptions, rejected promises, non-2xx responses). Assert the error surface, not just that it doesn't crash.
- Keep tests deterministic: mock network, filesystem, clock, and randomness. Don't depend on live external services or wall-clock time.
- Place tests by repo convention (`src/foo.ts` → `src/foo.test.ts` or a `tests/` mirror), one behavior per case, named by what they assert (`returns 400 when email is missing`, not `test email`). Reuse existing fixtures and helpers instead of duplicating setup.
- Cover the branches you touched — every new conditional, early return, and catch block gets at least one test — rather than chasing a global coverage percentage.
- Never leave failing, skipped, or stubbed tests behind. Don't `.skip` or comment out a test to make the suite green, and don't write always-passing assertions or `TODO` bodies.

Run before finishing: execute the suite (or at least the affected files) and confirm it passes. Report how many tests ran and passed and the exact command to reproduce (`npm test`, `pytest -q`, `go test ./...`). On Replit you can ask Agent to run the suite and fix specific failures. If a branch is genuinely untestable, leave a one-line comment explaining why rather than silently skipping it — and state which behavior the tests cover rather than claiming full coverage.
